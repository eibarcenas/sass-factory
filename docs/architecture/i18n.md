# i18n — Internationalization

## Strategy

```
Languages:   es-MX (primary) | en (secondary)
Scope:       dashboard UI + storefront UI + error messages
Dynamic content (business names, product descriptions):
             NOT translated — comes from Firestore as owner wrote it

Library:     next-intl (App Router native, RSC compatible)
             One package for both apps
```

## File Structure

```
apps/storefront/
└── messages/
    ├── es.json       ← default
    └── en.json

apps/dashboard/
└── messages/
    ├── es.json
    └── en.json
```

## Locale Detection — middleware

```typescript
// apps/dashboard/middleware.ts
import createMiddleware from 'next-intl/middleware'

// next-intl detects locale from:
//   1. Cookie 'NEXT_LOCALE'
//   2. Accept-Language header
//   3. Default: 'es'
export default createMiddleware({
  locales:       ['es', 'en'],
  defaultLocale: 'es',
})

export const config = {
  matcher: ['/((?!_next|api|healthz).*)'],
}
```

## Usage in Components

```tsx
// Server Component
import { getTranslations } from 'next-intl/server'

export default async function BusinessesPage() {
  const t = await getTranslations('business')
  return <h1>{t('create')}</h1>
}

// Client Component
'use client'
import { useTranslations } from 'next-intl'

export function BusinessForm() {
  const t = useTranslations('business')
  return <label>{t('name')}</label>
}

// With interpolation (error messages)
const t = useTranslations('errors')
t('SLUG_TAKEN', { slug: 'gorras-bebe' })
// → "El nombre 'gorras-bebe' ya esta en uso, prueba con otro"
```

## Rules

- Backend **never** returns human-readable strings — only `{ code, context }` (see `architecture/error-handling.md`)
- `context` object keys match placeholder names in i18n messages: `{slug}`, `{max}`, `{maxMb}`
- `useApiError()` hook bridges API errors to i18n strings (see `development/notifications.md`)
- Never hardcode Spanish strings in component JSX — always use `t()` even for static UI text
